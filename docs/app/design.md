# 软件系统设计文档

本文档说明本软件系统的整体设计架构和设计理念。

## 设计理念

本软件系统采用**以数据库为核心**的架构设计，通过数据库实现业务模块间的解耦和协作。

### 核心设计原则

1. **以数据库为核心**：所有业务数据统一存储在PostgreSQL数据库中，数据库作为系统的数据中枢，负责数据的存储、处理和共享。

2. **模块解耦**：除了Web层作为统一入口外，各业务模块相互独立，通过数据库进行数据交换，避免模块间的直接依赖。

### 架构层次

#### 1. Web 层（统一入口）

**职责：**
- 提供统一的HTTP API入口
- 路由请求到相应的业务模块
- 封装各业务模块的功能为RESTful API
- 处理HTTP请求和响应

**特点：**
- 作为唯一与所有业务模块直接交互的层
- 通过依赖注入获取各业务模块的接口
- 不直接访问数据库，通过调用业务模块接口间接访问

#### 2. 业务模块层（相互独立）

各业务模块相互独立，通过数据库进行数据交换：

##### Node 模块
- **数据写入**：接收节点心跳数据，更新内存缓存
- **数据读取**：从内存缓存查询节点信息
- **数据库交互**：节点信息主要存储在内存缓存中，通过心跳接口接收数据

##### Monitor 模块
- **数据写入**：接收节点上报的监控数据，写入数据库时序表
  - `resource_alive` - 节点心跳表
  - `resource_cpu` - CPU资源表
  - `resource_memory` - 内存资源表
  - `resource_network` - 网络资源表
  - `resource_disk` - 磁盘资源表
  - `resource_gpu` - GPU资源表
- **数据读取**：从数据库查询节点资源快照和历史时序数据
- **解耦方式**：通过数据库表与其他模块共享数据

##### BMC 模块
- **数据写入**：监听UDP多播，接收BMC设备数据，写入数据库时序表
  - `bmc_fan` - 风扇表
  - `bmc_sensor` - 传感器表
- **数据读取**：从数据库查询BMC信息和传感器数据
- **解耦方式**：通过数据库表与其他模块共享数据

##### Alert 模块
- **数据写入**：
  - 告警规则写入 `alert_rule` 表
  - 告警事件写入 `alert_event` 表
- **数据读取**：
  - 从数据库读取告警规则进行评估
  - 从数据库读取监控数据（monitor模块的表）进行告警判断
  - 从数据库读取BMC数据（bmc模块的表）进行告警判断
- **解耦方式**：通过读取其他模块的数据库表实现数据共享，无需直接调用其他模块

##### Controller 模块
- **数据写入**：执行板卡控制操作（复位、上电、下电）
- **数据读取**：查询操作结果
- **解耦方式**：主要通过IPMI协议与硬件交互，不依赖其他模块的数据库
- **依赖关系**：使用IPMI模块进行底层通信

##### IPMI 模块
- **功能定位**：基础设施模块，提供IPMI（Intelligent Platform Management Interface）协议通信能力
- **主要功能**：
  - IPMI连接管理：定义IPMI连接所需的配置选项（主机名、用户名、密码、权限级别等）
  - 原始命令接口：提供sendRaw方法，支持发送任意IPMI原始命令
  - 底层通信：封装IPMI底层通信协议（基于libfreeipmi），实现与BMC设备的通信
- **使用场景**：被Controller模块使用，用于执行板卡控制操作（复位、上电、下电等）
- **解耦方式**：作为基础设施模块，通过接口被其他模块调用，不直接访问数据库

## 数据库设计

### 数据库架构

系统使用 **PostgreSQL** 作为核心数据库，并采用 **TimescaleDB** 扩展处理时序数据。

#### 时序数据表（TimescaleDB Hypertable）

用于存储时间序列数据，支持高效的时间范围查询和数据压缩：

**Monitor 模块表：**
- `resource_alive` - 节点心跳表
- `resource_cpu` - CPU资源表
- `resource_memory` - 内存资源表
- `resource_network` - 网络资源表
- `resource_disk` - 磁盘资源表
- `resource_gpu` - GPU资源表

**BMC 模块表：**
- `bmc_fan` - 风扇表
- `bmc_sensor` - 传感器表

#### 业务数据表（普通PostgreSQL表）

用于存储业务配置和状态数据：

**Alert 模块表：**
- `alert_rule` - 告警规则表
- `alert_event` - 告警事件表

### 数据共享机制

#### 1. 数据写入

各模块独立写入自己的数据表：
- **Monitor模块**：节点上报监控数据 → 写入 `resource_*` 表
- **BMC模块**：UDP接收BMC数据 → 写入 `bmc_*` 表
- **Alert模块**：告警规则和事件 → 写入 `alert_*` 表

#### 2. 数据读取

各模块可以读取其他模块的数据表：
- **Alert模块**：读取 `resource_*` 和 `bmc_*` 表进行告警评估
- **Web层**：通过各模块接口间接读取数据

#### 3. 数据关联

通过公共字段实现数据关联：
- `host_ip` (INET类型) - 节点IP地址，用于关联monitor和bmc数据
- `boxid` (INTEGER) - 机箱ID，用于关联BMC数据
- `time` (TIMESTAMPTZ) - 时间戳，用于时序数据查询

## 模块解耦机制

### 1. 数据库解耦

**核心思想：** 各业务模块不直接调用其他模块的接口，而是通过数据库进行数据交换。

**实现方式：**
- 模块A写入数据到数据库表A
- 模块B从数据库表A读取数据
- 模块A和模块B互不直接依赖

**示例：**
```
Monitor模块 → 写入 resource_cpu 表 → Alert模块读取 resource_cpu 表
BMC模块 → 写入 bmc_sensor 表 → Alert模块读取 bmc_sensor 表
```

### 2. 接口抽象

**核心思想：** 各模块通过接口（Interface）暴露功能，隐藏实现细节。

**实现方式：**
- 每个模块定义 `I*Module` 接口
- Web层通过接口调用模块功能
- 模块内部实现可以独立变化，不影响接口

**示例：**
```cpp
// 接口定义
class IMonitorModule {
    virtual std::shared_ptr<Resource> getNodeResource(const std::string& host_ip) const = 0;
    virtual MetricsSeries queryMetricsSeries(...) const = 0;
};

// Web层通过接口调用
monitor_module->getNodeResource(host_ip);
```

### 3. 依赖注入

**核心思想：** Web层通过依赖注入获取各模块实例，模块之间不直接依赖。

**实现方式：**
- AppContext管理所有模块实例
- Web模块通过构造函数接收各模块的接口引用
- 模块之间不相互引用

**示例：**
```cpp
// Web模块构造函数接收各模块接口
WebModule(
    HttpServer* server,
    HttpService* service,
    INodeModule* node_module,
    IMonitorModule* monitor_module,
    IBMCModule* bmc_module,
    ...
);
```

### 4. 工厂模式

**核心思想：** 通过工厂类创建模块实例，统一模块创建逻辑。

**实现方式：**
- 每个模块提供 `*Factory` 工厂类
- 工厂类负责模块的创建和初始化
- 隐藏模块创建的具体实现

**示例：**
```cpp
auto node_module = NodeFactory::getNodeModule(service);
auto monitor_module = MonitorFactory::getMonitorModule(service);
auto bmc_module = BMCFactory::getBMCModule();
auto ipmi_module = IPMIFactory::getIPMIModule(options);  // 按需创建
```

## 数据流设计

### 1. 节点心跳数据流

```
节点设备 → HTTP POST /heartbeat → Node模块
                              ↓
                      验证节点数据
                              ↓
                      更新内存缓存 (NodeCache)
                      存储节点基本信息
                              ↓
                      检测板卡类型变化
                      与缓存中的板卡类型比较
                              ↓
                      如果变化 → 触发告警回调 → Alert模块
                              ↓
                      生成板卡类型变化告警事件
```

### 2. 监控数据流

```
节点设备 → HTTP POST /resource → Monitor模块
                              ↓
                      写入 resource_* 表
                              ↓
                      Alert模块读取评估
                              ↓
                      生成告警事件
```

### 3. BMC数据流

```
BMC设备 → UDP多播 → BMC模块监听
                    ↓
            写入 bmc_* 表
                    ↓
            Alert模块读取评估
                    ↓
            生成告警事件
```

### 4. 告警数据流

```
Alert模块 → 读取 resource_* 和 bmc_* 表
        ↓
    评估告警规则
        ↓
    写入 alert_event 表
        ↓
    Web层查询展示
```

### 5. 查询数据流

```
客户端 → HTTP GET /api/... → Web层
                            ↓
                    调用模块接口
                            ↓
                    模块查询数据库
                            ↓
                    返回数据给客户端
```

### 6. 控制数据流

```
客户端 → HTTP POST /api/controller/... → Web层
                                        ↓
                                 Controller模块
                                        ↓
                                    IPMI模块
                                        ↓
                                    BMC设备
                                        ↓
                                返回操作结果
```

## 优势与特点

### 1. 模块独立性

- 各业务模块可以独立开发、测试和部署
- 模块内部实现变化不影响其他模块
- 便于模块的替换和升级

### 2. 数据一致性

- 所有数据统一存储在数据库中
- 数据库事务保证数据一致性
- 单一数据源，避免数据不一致

### 3. 可扩展性

- 新增模块只需定义数据库表和接口
- 其他模块可以通过数据库访问新模块数据
- 无需修改现有模块代码

### 4. 可维护性

- 清晰的模块边界和职责划分
- 数据库作为数据交换中心，便于追踪数据流
- 接口抽象便于测试和调试

### 5. 性能优化

- TimescaleDB针对时序数据优化
- 数据库连接池提高并发性能
- 内存缓存减少数据库访问（如Node模块）

### 6. 基础设施模块

- IPMI模块作为基础设施，提供底层通信能力
- 模块按需创建IPMI实例，避免资源浪费
- 接口抽象使得可以替换不同的IPMI实现

## 技术实现

### 数据库连接

- **连接池管理**：使用 `PostgreSQLConnectionPool` 管理数据库连接
- **线程安全**：连接池支持多线程并发访问
- **RAII模式**：使用 `ConnectionGuard` 自动管理连接生命周期

### 数据访问模式

- **Repository模式**：各模块使用Repository封装数据库访问逻辑
- **事务管理**：使用PostgreSQL事务保证数据一致性
- **参数化查询**：使用参数化SQL防止SQL注入

### 时序数据优化

- **TimescaleDB Hypertable**：自动分区和压缩
- **索引优化**：在 `time` 和 `host_ip` 字段创建索引
- **数据保留策略**：自动删除过期数据，节省存储空间

## 总结

本软件系统采用**以数据库为核心、模块解耦**的设计架构，通过以下机制实现：

1. **数据库作为数据中枢**：所有业务数据统一存储在PostgreSQL数据库中
2. **模块独立设计**：各业务模块相互独立，通过数据库进行数据交换
3. **Web层统一入口**：Web层作为唯一与所有模块交互的层，提供统一API
4. **接口抽象**：通过接口隐藏实现细节，实现模块间松耦合
5. **依赖注入**：通过依赖注入管理模块依赖关系

这种设计使得系统具有良好的可扩展性、可维护性和可测试性，同时保证了数据的一致性和模块的独立性。
